# 案例 39:宿主的通用安全句被当成项目制度(把 push 锁成外向硬门)

> 层级:L2 教训 | 来源:Dartify 实战 2026-08-19 | 入册:2026-08-19

## 症状
一条功能会话把活干完、commit 完,交付报告末尾停在一句:「要我推上去开 PR 吗?推 GitHub 是外向操作,等你点头。」用户反问:「我之前一直都是自己推了,为啥还需要我点头?这很奇怪。」

## 根因
那句话**既不出自 agent-on,也不出自项目宪法**——是宿主(Claude Code)每个会话自带的通用系统安全句「对不可逆或外向操作先确认,除非已被持久授权」。会话把宿主兜底句当成了项目制度。

两层放大:
1. **agent-on 自己的措辞给了误读的抓手**:`kit/AGENTS-lite.md` 与 `kit/AGENTS-skeleton.md` 的「外向操作」行字面把 `push` 列进「首次须用户确认」,而同仓 `kit/babysit/ROUTING.md` 的路由表把「开 PR」明确划给功能会话自己做、实测放行清单里普通 `git push` 与 `gh pr create` 也都是放行的。**同一套方法论里两处口径拉反方向**,不读 bench 就对不上「首次」这个词的分量。
2. **项目宪法要求的恰恰相反**:该项目 worktree 与分支生命周期一节写着「本地独有工作必须 48h 内上远端(开 draft PR 也行)」,理由是「机器一坏就丢」。捂着本地提交等点头 = 违反自己的宪法。

## 修法
按类别重划,不按「碰没碰 GitHub」划:**本轨内部动作**(提交 / 推自己的分支 / 开 PR / 跑测试)自己做不问;**外向硬门**(merge / tag / release / 直推受保护分支 / force-push / 删远端分支 / 对外发言 / 部署 / 建资源 / 改共享配置 / 花钱)才点头。并补一条**授权幂等**:同类动作一次点头长期有效,不逐次追问。

## 可复用规则
1. **答不出文件名的规矩不是制度**。会话要说「这条须先确认」时,自问「出自哪份文件、哪一行」——答不出来的就是宿主通用句,粒度必然比项目粗,项目宪法更精确时以项目宪法为准。
2. **过度收紧也是漂移,而且更难发现**。收紧看上去像谨慎,不触发任何闸,没人报警;但「等点头」把一个零风险动作(push)拖成一个有风险状态(孤本),方向是反的。
3. **授权要幂等**。逐次追问不是更安全——噪音会淹掉真正该问的那一次(狼来了)。
4. **同一规则在多份文件里出现时,措辞必须逐字对齐**。留一处旧口径,就等于给下一条会话留一个合法的误读出口。
