# 案例 49：两遍独立复核，看的是同一块地方 —— 换了人，没换搜索面

> 层级：L2 | 来源：Dartify 2026-09-26 结账（shared-search-surface-defeats-independent-review，#210 原文）+ 2026-09-26 Agent-On 消化会话同型现场 | 入册：2026-09-26

## 症状

- **Dartify #210（2026-08-20）**：对对齐审计的 19 条做「独立第二遍」复核，两遍互不参照。16 条完全一致——但条目 16 **两遍一起判错**：都判「仍开」，证据也一样，而修复早就做完了，躺在 worktree `funny-cartwright-00c54b` 的工作区里一直没提交（11 files / +152 / −162），当场抢救提交成 `8edb574`。同一批还查出一笔已提交但没推的 534 行（`ce648a1`）。commit 正文原话：「本次方法论最重要的一课:#16 两遍一致地错了」。
- **Agent-On 2026-09-21 草稿**：看到 CryptoQuant / aster-agent 的误拦症状，结论写成「闸体修复 deferred，须单独一轨」。没查拦人的是哪一份闸——拦截文案点名的是插件缓存 0.5.0 里的老 Python 闸，仓里的 Rust 闸早就修好了（案 46 / 47）。
- **本场自己也差点踩**：消化开在一棵从 origin/main 切出来的 worktree 里，`ls intake/` 看不到任何未跟踪的卡；只在这棵树里找，结论会是「没有积压」（案 48）。

## 根因

**「独立」被理解成换一个人（或换一个实例），搜索面却没换。** 两个复核者都只看 main 加当前树，共同的盲区——别的树的工作区、没推的提交、宿主上实际在执行的那份副本——一个都破不了。两遍一致，看起来像是强证据，其实只证明了两次测量用的是同一把尺子。

否定结论（「X 还没做」「X 不存在」）尤其危险：肯定结论能贴出命中，否定结论只能贴出「没找到」，而「没找到」首先取决于你在哪里找、用什么找。

## 修法

- 否定结论落盘前两件事：① 拿一个已知必中的样本跑同一条命令做**正对照**，贴命令和命中数；② 搜索面覆盖其余 worktree 与全部 ref（`git worktree list`、各树 `status --porcelain`、`git log --all -- <file>`），涉及工具行为时再加一条：**实际执行的是哪一份**。
- Dartify 在 #207 已把「零命中先跑正对照」「否定结论贴命令与命中数」写进项目的 `design/features/README.md`；本批提到方法论层。

## 可复用规则

**独立复核要换搜索面，不只是换人。** 两遍结论一致时先问：它们看的是不是同一块地方？否定结论不贴正对照与搜索范围，不算结论。
