# 2026-10-25 · Agent-On 取舍与 Matt Pocock 方法接入审视

> 职责边界：本文件保存本轮产品与代码审视、用户已确认的方向、建议取舍及首批验收；不是已实施清单，也不替代 CHARTER、值守授权或现行执行书。HTML 取舍图是本文件的临时展示。本轮只新增此快照，未删除功能、改动运行规则或发布版本。

## 1. 用户已确认什么

- “Agent R”指当前 Agent-On。
- 用户反馈：模型变强后，Agent-On 几乎很少用；此前的 Dashboard 没有产生使用价值。
- 值守有价值，应保留；希望 Agent-On 还有其他实用能力。
- 希望借鉴 Matt Pocock 的地图、代码设计与执行方法，使能力连接起来。
- 三种用途之中，用户明确优先选择：**跨窗口统筹：分工、跟进、合并**。
- 用户追加优先级：**少打断、加快开发与合入**。CI/review 已占用过多时间；希望综合质量检测按周集中，适应开发中持续变化的需求。具体检查如何分层见 §12。

因此本轮推荐的主线是：**让一个入口统筹多个执行窗口，把目标变成工作包，跟进真实卡点，验收结果并交给值守合入。** Matt 的方法帮助工作包定义与实现，Agent-On 负责项目上下文、协作关系、交付证据与既有权限。是否改写产品宪章、具体删哪些兼容入口及自动推进授权范围，尚未由本轮审视决定。

## 5. Matt 的“地图”应怎样结合

这三张图回答不同问题，不应合成一个大而全 Dashboard。

| 图 | 回答什么 | 在 Agent-On 的用途 |
|---|---|---|
| `wayfinder` 决策地图（原名 decision-mapping） | 去哪里？哪些问题还没定？哪些问题得先解决？ | 只用于跨多个会话、方向仍不清的大目标；记录决策与证据，不把“问题已决定”当成“代码已完成” |
| `to-tickets` / `implement-spec` 任务依赖图 | 谁做哪件完整工作？依赖完成后谁可以开始？ | **本轮最值得接入。** 工作包对应现有 task ID 和责任窗口，复用已有依赖与合入判定；先处理共享文件，再并行独立部分 |
| `improve-codebase-architecture` 代码关系图 | 改动涉及哪些 Module？哪些复杂度能删除或集中？ | 派工前只看会碰到的区域；避免把同一个共享 Module 拆给多个写者，也避免按文件大小盲目拆代码 |

`GLOSSARY-MAP.md` 是多领域词汇的索引，不是任务调度器。Agent-On 当前没有这类多领域需求，不为“有张地图”先新增一套词汇体系。

决策详情仍落已有 snapshot / 项目决策源，工作包详情复用已有任务卡或 tracker，运行事实仍认 Git 与现有回执。图只保存指针和关系；不要把内容再抄到 progress、Dashboard、Issue、台账四个地方。

## 6. Matt 技能接入位置与需要改写的部分

| 环节 | 借鉴来源 | Agent-On 落点与完成条件 |
|---|---|---|
| 明确目标与未知问题 | grilling、domain-modeling；大目标才 wayfinder | 统筹核现有目标，只问代码和证据无法回答的决策；沿用既有 snapshot，不再额外铺一套 ADR |
| 定义工作包 | to-spec、to-tickets | 一张工作包包含可验收的完整行为、范围、依赖、责任窗口及证据位置；复用现有 phase/task/tracker，不重复播种 |
| 安排可开工任务 | implement-spec 的 task graph / frontier | 依赖已真正合入、范围无冲突且已有对应派工授权的工作才能推进；缺授权只挂起相关动作，其他已授权工作继续 |
| 执行与排错 | codebase-design、tdd、diagnosing-bugs | 执行窗口优先通过用户可观察的行为验证；真实缺陷先建立能失败的复现，样式/文档按风险做检查，不把全部任务强制 TDD |
| 验收与审查 | code-review 的 Standards + Spec 两轴 | 按可交付批次回答“符合关键约定吗”与“完成当前需求了吗”；局部验证随改动，全仓体检按周，问题修正后只复查受影响范围。Matt / GStack / kit 同阶段只选一套；分层见 §12 |
| 合入与发布 | 现有 oncall / landing / merge-audit | 工程 skill 交验收结果，值守按既有权限串行合入并记账；交付仍锚定真实提交与 PR |
| 复盘与回流 | retro、writing-for-agents | 机械重复错误尽量修检查，判断类问题才修说明；删无效规则也算改进；沿 loop-notes → intake → 消化，不另建知识库 |

**不能照搬的地方：**

- `implement-spec` 原版让 merger 子代理合入、执行者合并 integration branch，并清理各工作树。这里合入、追平、对外通信与跨窗口中转仍按值守规则；回收按既有授权，不能因套用了 skill 获得删除权。
- 原版按可用任务自动派 implementer，不等于本仓已获得任意跨工具、跨模型或新聊天授权。优先复用用户指定的窗口；实际创建和发消息走宿主权限与现有登记，不假造绑定或把另一任务的消息当人类授权。
- 原版 `to-spec` 的长用户故事清单、每任务固定 TDD、每次交互重新确认，不能重新变成轻量工作的必经关卡。
- `wayfinder` 的地图完成只代表路线清楚，不代表获得实施批准；记录者不能靠改自己的 Notes 自授权限。
- 多个用户调用型 skill 带 `disable-model-invocation: true`。当前可读到文件，不等于日常入口可自动调用。可自动复用的少量方法应整理为 Agent-On 自有参考文档并注明来源；保留第三方显式调用方式，不改插件权限或假称“全部接通”。
- 本轮没有安装、升级或复制 Matt 插件。若以后复制实质内容，应保留其 MIT 许可与署名；优先接上方法和产物约定，而非 vendor 整套流程。

## 7. 四个可实施候选

### A · 把分工、跟进、交单接成一条入口（Strong）

**涉及**：`skill/SKILL.md`、`kit/patrol-control-plane.md`、`kit/track-prompt-template.md`、`kit/babysit/`、`playbook/workflow-orchestration.md`，以及实际缺口对应的 coordination 能力。

**现状 → 建议**：用户逐项挑 patrol/dispatch/task/值守 → 原入口按目标和现有任务关系生成工作包、核依赖、按授权协调窗口、收证据和交单。值守在班时所有跨窗口指令经值守；这些是同一条工作链，不强制新增“总管”“巡逻员”等常驻聊天。

**删除检验**：删掉重复角色说明和手工转述步骤，复杂度会减少；删掉工作包与责任关系，复杂度会重新落回用户。Depth 应体现在用户少做协调，不是多了多少命令。

**验收**：一个真实“共享改动 + 两项独立改动”目标，用户无需逐窗口复述上下文；前置成果未合入不能开消费者，结果带验收证据，合入归现有值守。不以准备好 prompt 或返回 thread ID 冒称执行就绪。

### B · 项目简报脱离网页（Strong）

**涉及**：`cli/src/dashboard.rs:60`、`cli/src/main.rs:64`、`cli/src/session.rs:139`、`cli/src/system_dashboard.rs` 与两份 HTML。

**现状 → 建议**：status/续接通过 Dashboard 读取多处事实 → 独立的项目简报 Module 为原窗口和值守提供文本/JSON，网页只是可移除的 Adapter。保留 PR 证据年龄、未知/损坏状态，不把“没有活动源”显示成“无人工作”。

**删除检验**：展示 Implementation 可退场；事实汇总若删除，多个调用者就要重复读任务、会话、值守、PR 和 worktree。它有真实 Leverage，应保留。

**验收**：不开网页也能读当前目标、任务/责任窗口、阻塞、待验收、待合入和下一步；主树与 linked worktree 同源；损坏与陈旧明确显示。沿已有 CLI Interface 验证，不给每个内部函数加镜像测试。

### C · 合入证据从清道夫中独立（Strong）

**涉及**：`cli/src/coordination.rs:1184` → `cli/src/janitor.rs:201` / `:226` → `cli/src/worktree.rs` 的 `run_gc`。

**现状 → 建议**：派工依赖清道夫，清道夫解析整套 GC 报告判定合入 → 交付证据 Module 集中真实合入判断，派工和回收各自消费。Seam 放在“成果是否被目标分支覆盖”，不暴露回收报告的内部形状。

**删除检验**：可以减少清理能力；不能把 released_head、祖先检查、squash 后新增提交保护一起删掉。集中这些判据提高 Locality，避免两处各自猜测“已合并”。

**验收**：released 但未合入仍阻塞；squash 已覆盖的提交可识别；PR 合并后又新增提交仍保护；取证失败为未知/阻塞，不能报成功。已有 coordination 与 worktree 测试可复用。

### D · 状态解释与宿主派工收拢（Worth exploring，后置）

**涉及**：`cli/src/coordination.rs:220` / `:803` / `:1531` / `:1802`、`cli/src/activity.rs:318`。

**现状 → 建议**：任务状态、窗口活动、进程与结果散在不同调用路径 → 统筹集中解释这些事实；具体启动仍由各宿主 Adapter 完成。多宿主确有不同，Seam 有依据；不为大文件本身重构。

**保留区别**：工作包是否完成、窗口是否在运行、是否收到自述、代码是否验收、是否合入，是五件事。不能揉成单个百分比，也不能用 Stop 触发下一阶段。

**验收**：迟到/重复事件不复活已释放任务，不覆盖作者阻塞；重试复用真实绑定，缺 ID 不猜最近会话；只在有意义的状态变化时提醒。

## 8. 建议的首批范围与顺序

用户优先级为跨窗口统筹，并追加“少打断、加快开发”。**首批先减少无关检查与重复 review（§12），再接 A + B**；C 是可靠推进依赖任务与后续缩减 janitor 前的必要整理；D 等真实任务暴露缺口再动。减少等待本身就是统筹的验收目标。

| 顺序 | 可交付结果 | 依赖与验收 |
|---|---|---|
| 0 · 理清现有改动 | 逐项保全/接纳/缓议既有未发布工作，主树与 v0.28.2 基线对齐 | 不携带整批旧草稿发版；不 reset 他人工作；只在实际开始代码批时处理 |
| 0.5 · 缩短合入路径 | 检查按影响范围分流；综合周检；批次审查和局部复查 | 先落实 §12 的 CI、值守判定、审查模板三处一致；未验收的必需检查不能冒称通过 |

## 11. 追加审视：结账 / digest 是否已被模型内化

### 用户反馈与结论

用户补充：现在已经很少调用 digest、结账，询问 Agent-On 的迭代发展是否仍需要保留，是否已经被大模型内化。

**建议修正：保留有证据的改进闭环；不把手工结账、专场消化和不断增加规则作为日常使用要求。** 前文“保留闭环”不等于原样保留全部手续。以下是审视建议，尚未改写 settlement、跨仓边界或发布规则。

“模型内化”需要分开看：

| 层面 | 本轮判断 | 应留下什么 |
|---|---|---|
| 通用推理与工程习惯 | 总结、归纳、拆问题等方法是否仍需额外提示，必须与当前模型的默认表现比较；单凭少用口令不能证明已经内化 | 没有改变实际行为的提示退出默认；只保留有本项目证据的例外与约束 |
| 项目记忆与宿主记忆 | 已有证据表明部分经验进入宿主记忆，而非 Agent-On 指定账本；这属于外部持久记录，不等于模型权重学会了这些事实 | 尽量复用记录实际存在的位置，不要求复制一遍到 loop-notes |
| 跨项目方法与工具演进 | 一个窗口的总结不证明另一个宿主已读取、不证明共用工具已修复、不证明运行版本已更新 | 保留问题证据、最小修正、验证、相关执行面生效与后续效果这条链 |

本轮没有对不同模型做有无提示的对照实验，因此不声称某条具体规则已经被当前模型完全吸收。

### 已有证据说明什么

1. [Dartify 09-26 回流](../intake/2026-09-26-dartify.md)记载：上次结账后新增 **138 个提交**，loop-notes 没有新增；同期宿主记忆 **19 个文件**发生变化，审阅者识别出其中 9 条协作教训。这个历史案例支持“经验记录位置已经迁移”，不能据此推断所有记忆都会自动跨宿主共享。
2. [09-29 回流](../intake/2026-09-29-dartify.md)和 [10-08 回流](../intake/2026-10-08-dartify.md)明确说明不是完整结账，而是现场问题投递。说明用户不执行整套口令，真实反馈仍可出现；值得把这种路径作为主路候选。
3. [10-08 执行器升级](2026-10-08-oncall-executor-upgrade.md)记载：身份修复已经发布，实际运行的执行器仍旧；随后更新执行面，原 Dartify 窗口的真实回执仍待确认。这类差距不能靠模型“记住应该怎么做”消除。
4. 现行 settlement 仍要求候选整理、六项卡片、项目回执、提示切仓、专场消化、逐卡提交及发布；还用案例数/篇数播报成长。这是实际成本与代理指标。它是否导致用户少用，本轮只能列为解释，不能宣称已测得因果。
5. 本次读取的 session / capture / activity 路径主要记录会话、任务与观察事实，没有看到把教训自动核验、改规则、发布、验证收益的完整实现。当前应称为“有反馈流程”，不能称为已经运行的自我学习系统。

### 怎样接到跨窗口统筹

建议把改进动作贴在已有工作包验收与合入收口上，不另开常驻复盘模型，不检查每次工具调用，不创建新的学习数据库。

```text
真实任务交付
  └─ 出现返工、用户纠正、误拦、重复传话或旧规则不合身
       └─ 先判断原因：实现缺陷 / 安装与接线 / 项目知识 / 共用流程
            ├─ 项目问题：在原项目授权范围内修正并验证
            ├─ 工具已有修复：核相关执行面，按已有升级授权处理
            ├─ 通用规则无效：删除、合并或缩小适用范围
            └─ 确需跨项目修正：沿已有 intake 留证据，Agent-On 仓维护
                 └─ 实际相关任务再次使用后，记录有效 / 无效 / 待验证
```

统筹负责把跨窗口发生的事实收齐、定位责任与提出改动；执行窗口的自我总结只作为线索。共享规则仍由 Agent-On 仓维护，项目端只投递材料。没有有价值的改动就正常结束任务，不为完成闭环而生造卡片。

**保留 / 收缩的具体建议：**

- `settle`：保留为显式批量补收与历史材料导入入口；日常有证据的问题可直接单项投递，不再要求用户记住“到时间结账”。
- `digest`：保留为维护者整理多个来源、决定共享改动的入口；有明确可复现 bug 时直接进入正常修复工作，不必先举办一场方法论消化。没有待处理问题则安静，不制造消化任务。
- `loop-notes` / 宿主记忆：复用已有来源，按需留证据指针；不再要求同一教训多处复制。业务知识留项目，个人偏好沿个人配置管理，Agent-On 只收协作方法与自身工具的问题。
- 卡片与审批：保留能解释问题、证据和落点的信息；六项字段、强制换会话、逐卡提交等手续列入后续精简范围。已有明确授权的可逆修正按授权推进，验证强度不能替代权限判断。此处没有撤销当前硬规则。
- 机械问题优先修工具或检查；只有确需判断的约定才进入文档。这是 Matt `retro` 与 `writing-for-agents` 最适合内化的部分。
- 进化必须包含规则退场。尤其是 Agent-On 自己制造的误拦和文书负担，优先修掉原因，不在外面继续包一条操作规矩。
- 发布与相关执行面检查仍保留；不把“少用结账”外推成“不需要版本和验证”，也不自动升级其他项目或改宿主配置。

### 判断迭代是否值得继续

观察下一件真实统筹任务：同类错误是否减少、用户转述是否减少、阻塞是否更快解决、流程是否更短。一次任务只形成案例；没有后续验证就标待验证。

若一条规则在缺省模型/宿主能力下已无增益，且移除后相关行为仍可验证，退出默认或删除。若一批记录不能指向任何值得修改的代码、配置或约定，就停止追加处理成本，不以卡片数、文档数、版本数证明成长。

这意味着 Agent-On 演进的对象是**实际工作环境与协作方式**：模型帮助诊断和改进，证据判断改得是否有效。无需把每次成功都包装成“学习”，也不能把模型会总结当成跨项目闭环已经完成。

## 12. 追加审视：减少 CI / review 等待，综合质量检查按周

### 结论与证据

**建议采用：开发时局部验证，交付批次做一次审查，合入只等相关必需检查，每周集中做综合体检。** 周检从日常合入路径移出，不把一周的改动攒成一个巨大 PR。需求探索期间，以用户当前确认的行为验收；没有改变结论的新证据，就结束已完成的检查。

2026-10-25 核对到的具体负担：

| 证据 | 判断与改法 |
|---|---|
| `gate.yml` 的 `cli` job 对每个 PR 无条件执行 fmt、clippy、全套 Rust 测试和 intake-lint；main push 再触发。已有缓存与 cancel-in-progress | 纯文档改动也跑 Rust，值得按影响范围拆开。PR 与 main 可能测试不同提交，不能一概称为相同证据重复；先明确各自验证目的 |
| `merge_audit.py::merge_health` 遍历整个 statusCheckRollup，按 policy 中的红色结论阻塞，不区分必需与建议检查 | 单把周检改成 GitHub 非必需还不够；值守判定与机器策略要一起对齐。`kit/merge-checklist.md` 已有区分外部噪声的文字，实现尚未表达同样的边界 |
| `kit/review-prompt-template.md` 要求“假定其中有至少一个缺陷”，逐项独立重跑；failed 中混列 Minor，再进入复审循环 | 容易诱导找问题和重复取证。改成证据驱动；风格/可选重构与影响当前验收的缺陷分开，修复后只复查受影响部分 |
| [Dartify #606](https://github.com/PBD-Academy/Dartify/pull/606) 的 diff 仅含 docs 下记录、任务与目录文件；[CI 运行](https://github.com/PBD-Academy/Dartify/actions/runs/40072214638)跳过了六个平台 job，但 state job 仍有 42 个步骤（含 setup 与收尾），包括配色生成、边界自测、设计变量核对等 | 下游已有分流，问题不是“什么都全跑”。仍需拆分通用 state job，让无关领域检查不跟着记录改动执行；记录一致性与密钥检查仍有实际用途 |
| 抽查 [Dartify #616](https://github.com/PBD-Academy/Dartify/pull/616) 提交 `4b7193a` 关联的 [CI 运行](https://github.com/PBD-Academy/Dartify/actions/runs/40162618793)：desktop 在隔离 Linux 显示验证步骤失败，web 被取消 | 与本次桌面改动相关的失败仍需分诊；仅凭 job 状态不能判定是代码、环境或调度原因。这个样本不能靠“改为周检”直接宣告可合入 |

以上远端抽样只读。接口没有返回运行时长，本轮没有读完日志，也没有取得分支保护配置；不能把 PR 创建到合入的全部时间算成 CI 耗时，不能据此声称已定位所有慢点。

### 建议的默认节奏

| 时点 | 做什么 | 对推进的影响 |
|---|---|---|
| 开发过程中 | 运行与改动直接相关的测试、复现或预览；修 bug 时先证明复现能失败 | 自动完成，不逐步向用户确认；不为每次编辑启动全仓 review |
| 一个可交付批次完成 | 一次需求与关键约定审查；相关行为验证。有关联的小任务共用一次整体验收 | 发现影响当前交付的实质缺陷才返工；可选重构、风格建议按价值处理，不自动卡合入 |
| 准备合入 | 当前候选的必要编译/类型/关键行为检查、相关安全与数据边界检查；值守核合入条件并记账 | 相关必需检查通过即可按已有授权推进，不等周检。依赖或共享接口变化要覆盖消费者；取消/未知不能伪装成功 |
| 每周一次 | 全仓回归、跨平台广覆盖、架构与重复代码审视、性能趋势、文档与工具规则漂移 | 后台集中处理，正常无变化保持安静；只带回值得行动的问题、负责人和证据 |
| 相关高风险改动或生产发布 | 提前做该变化所需的完整回归与发布核验 | 不等下一周。若 main 合入即自动生产部署，先把发布必需检查算入合入路径，不能先放行再补 |

“只做相关检查”依赖可信的影响判定。涉及共用基础、依赖锁、检查器或 CI 本身，或影响范围判断不清时，扩大到对应完整测试。全仓周检保留交叉发现的能力；它发现的真实严重缺陷仍应及时修复。不能仅因某个检查被叫作 advisory，就忽略已确认的当前交付风险。

### Matt 接入如何减轻

- **地图按需**：范围明确的任务直接实现；只有跨窗口依赖或方向未知才画对应地图，图里复用已有任务与决策。
- **实现时局部、批次末整体验证**：原版 `implement` 已写局部测试经常运行、全套在工作结束时运行一次；`implement-spec` 又安排集成后的整体 review。原样叠加仍可能重复，Agent-On 应按一个可交付批次安排一次适当范围的完整验证和审查。
- **保留 Standards / Spec 两个问题**：关键项目约定是否满足、当前需求是否完成。它们是两个判断角度，不等于每个小任务都必须启动两名审查代理。原版明确要求跳过工具已经检查的内容，并把代码气味当启发式判断；不再叠加另一套 GStack 或 kit 全流程。
- **以当前需求为准**：用户改变要求后，就地更新工作包验收及来源，旧假设明确作废；审查比较当前约定。已有上下文能确定的事实由代理读取，只向用户追问会改变产品方向且无法确定的问题。
- **复查有边界**：修复后核修复点与影响范围；同一提交、环境和范围下已有可信通过证据可复用。提交、依赖或集成环境变化影响证据时，重跑相关部分。出现新缺陷才扩大检查，不因完成一轮就自动开启下一轮。
- **改善自身负担**：把误报、重复检查、等待用户与迟迟无法合入作为 retro 的输入；无增益的规则可以删除，不以审查轮数证明认真。

这是 Agent-On 自有接入约定的设计，来源为本机 Matt Pocock 1.3.1 的 `implement`、`implement-spec`、`code-review`、`writing-for-agents`。没有修改安装缓存，也没有宣称已执行原版 code-review 的双代理流程。

### 第一批实际修改应落在哪里
