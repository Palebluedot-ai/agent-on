# 2026-10-02 · 易用性与自我改进闭环 review

> 职责边界：记录 v0.26.0 升级后的产品评审、实际缺口与下一轮开发验收。这是开发建议，不是新增权限、已经实现的功能或新的执行规则；产品权威仍为 CHARTER，现行操作按 boot / kit 执行。
> 基线：HEAD / v0.26.0 = `0c6e5dc07f4332d03d1332b940ef169fbb4e90db`。用户希望继续把 Agent-On 做得好用、易用，保留结账与消化的初心，并具有可持续自我改进的特征。

## 1. 本轮判断

Agent-On 已有采集、结账、消化、发版、升级六站。v0.26.0 已允许规则删除、收缩、合并和有理由不改；巡逻、跨模型派工与清道夫也已有第一版。

下一阶段的主目标建议是：**让真实任务不断改善 Agent-On 的规则、模板和工具，并让用户少操心。** 成长同时包括减少无效流程、修正误拦、提高续接质量和降低协作冲突。

当前最薄的一环是改动后的效果验证。卡片标为 landed、测试通过、发布新 tag，分别证明处理、局部验证和供货；后续项目确实少踩坑、少办手续，还需要真实使用证据。

可以借鉴 [Darwin Gödel Machine 论文](https://arxiv.org/abs/2505.22954) 的“修改自身工具与流程，再用外部任务评价改动”机制。这里是对 Agent-On 的设计借鉴：现有模型提出改进，文件和薄 CLI 承载改进，任务结果筛选改进。论文的收益不能移植成 Agent-On 的收益声明。[Self-Refine](https://arxiv.org/abs/2303.17651) 展示了用模型反馈迭代产物的方式；我们的默认验收仍须有可核任务结果，模型自评只用于提出候选。

## 4. 用户体验建议

用户继续在一个入口说目标和反馈。入口先复用已有任务与文件，决定直接做还是按需派工；巡逻把任务与冲突简表送到入口，值守按现行登记负责合入和跨窗口路由。清道夫作为受管后台作业呈现结果。

日常入口优先覆盖：**继续做、结账、升级**。Agent-On 仓内再提供消化入口。patrol / dispatch / janitor 等保留作高级操作，用户表达明确需求即可走对应执行书。

普通回复只回答当前进展、影响下一步的问题和实际下一步。明确任务不再重复确认；自动记录与验证不能变成用户必须填写的一套新表。

原窗口 compact 继续使用宿主原生机制，关键决定落现有任务记录。新会话是否必要由实际遗忘/绕圈情况决定；本轮没有做长任务压缩质量实验。

## 5. 自我改进的一圈如何闭合

**真实任务 → 摩擦证据 → 归因与候选改动 → 受控验证 → 消化发版 → 下游使用 → 效果回流。**

1. **观察事实**：例如共享组件冲突、同一授权被重复询问、误拦无关提交、压缩后重复工作。证据指向实际任务/commit/输出；不把业务知识或个人私有信息自动送进方法论仓。
2. **提出最小改动**：先判断环境/版本问题、执行错误、模型能力或规则设计的原因。候选可以是合并任务、缩小规则适用范围、删除旧默认或修 CLI；不以新增规则数量计成长。
3. **先验证候选**：复现原问题，再在受控任务检验改动，并核相关保护行为。收益标准来自原需求和预先确认的验收；候选不能靠改宽自己的评分标准得到成功结论。
4. **供货**：在现行授权内消化落地，完成回执与本仓规定的 tag 发布。权限和产品方向的改变仍按既有责任人判断，不从一张反馈卡推导授权。
5. **回访真实使用**：相关后续任务或下次结账记录效果；出现负收益就缩小范围、退出默认或回滚，并保留原因。没有新任务时写“待验证”，不虚构成功。

这些信息可以补在现有 intake 卡、bench 案例和 loop-notes，不先添加数据库、常驻评审模型或另一套日常台账。也不先把所有旧卡强制补齐新字段。

## 6. 三批开发与验收

| 批次 | 范围 | 完成标准 |
|---|---|---|
| A · 入口可靠 | Codex 安装命令与错误回执、构建/缓存顺序、上述闭环摘要漂移 | 受控新装机和已有安装升级得到真实结果；不支持/失败项明确；项目端结账不执行 Agent-On git；已授权升级不重复索取同一决定 |
| B · 成长可验证 | 自然入口、摩擦留痕、结账草稿去重、最小消化与效果回访 | 一条真实摩擦从原任务走到后续任务：证据可核、改动可回退、原问题改善、相关保护通过；只拒绝/缩小规则也能正确收口 |
| C · 协作实测 | 共享任务 + 两个页面、巡逻真实接线、跨模型结果、受控回收恢复 | 入口拿到真实任务回执和冲突提示；相关窗口覆盖可核；失败不会重复造树；受管回收后确实能恢复，保留未知/占用资源 |

A 先做；B 是下一阶段的主交付；C 复用已实现能力完成现场验收，不继续按角色数量扩项。每批收口可合并处理多项、一次发布与对应必要检查，避免每张卡、每个页面分别重复发版或启动同一组全量验证。

**同日追加 · 跨平台/云端接续**：用户随后指出 Claude/Codex 间看不到值守与提醒，并确认包含真正云端或远程环境。将“项目级启用、会话自动挂接、统一状态、真实角色身份”加入 A 的 P0；可携带配置与云端结果回传在 B 前半完成，再验证成长效果。详细设计与本机证据见 [跨平台与云端接续](2026-10-02-cross-platform-and-cloud-continuity.md)。仅同机共享 .git 内账本不足以覆盖云端；临时云任务先作为执行者接入唯一合入入口，不为每个平台复制同级值守。该追加仍是待开发方案，不代表角色已启用或云环境已接通。

收益观察复用已有任务证据：重复确认次数、真实冲突/返工、交付用时、CI 实际运行次数、相关风险遗漏。无基线或不可比时标未测，不承诺提速比例；单个任务只作为案例，后续独立任务再检验可迁移性。
