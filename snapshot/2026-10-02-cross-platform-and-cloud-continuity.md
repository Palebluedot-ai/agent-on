# 2026-10-02 · 跨平台与云端接续设计

> 职责边界：补充易用性开发计划中的项目级启用、自动接续与云端回执设计。本文是待开发方案，不代表已开启值守、已接通云端或修改了当前合并/授权政策。产品边界仍为 CHARTER：文件优先、薄 CLI、复用宿主能力。
> 基线：v0.26.0 / `0c6e5dc`。用户明确指出从 Claude 切到 Codex 看不到值守和提醒，并确认“Cloud”指真正云端或远程环境。希望以文件为基准，避免每个平台、每个窗口重复启用。

## 1. 产品约定建议

**项目启用一次；新会话自动挂接；已有角色优先复用；跨环境复用配置、任务和回执。**

用户只需表达本项目要启用哪些能力。宿主/执行环境的首次安装、登录和正常信任流程各自完成；后续会话由接入件自动读项目状态，不要求用户反复启动同一套值守和巡逻。跨平台接续以项目文件和实际结果为依据，不要求搬运厂商私有聊天历史。

项目已启用、宿主已接入、角色已启动、角色最近有活跃证据，是四个不同事实。新入口应简短呈现与当前任务有关的差异，不能从一行 enabled 推断有人值守。

## 3. 当前已有与缺口

- **已共享本机账本**：值守在 `<common-git-dir>/agent-on/oncall.json`，巡逻与任务在同目录的 `control/`。一个 clone 的 Claude/Codex 与 linked worktree 可读同份记录；不用为每个工具复制台账。
- **巡逻已有跨 host 复用基础**：`start_patrol` 查找任意 host 的活跃 patrol 回执，不按新入口 host 再造一个。此处是源码核查，不是跨厂商真实窗口实测。
- **自动发现还不完整**：capture 在 disabled 时直接退出，SessionStart 当前不输出项目角色摘要；已启用巡逻的需求提交只输出巡逻上下文。值守没有一条覆盖各宿主的开场提示路径。
- **值守身份太依赖目录**：`role_at` 与 `refresh_if_oncall` 按当前 repo root 是否等于登记 worktree 判断归属。源码显示同目录内不同真实会话可能都被当作值守；需核真实会话身份并加入行为回归，不能为区分身份强制每个窗口开 worktree。
- **不同 clone/环境各有 .git**：相同 remote URL 不是同一个本地账本。云端通常取得工作仓内容，不取得本机 .git 内运行记录、用户级 skill、插件缓存和活进程。

## 4. 文件为基准的三层

| 层 | 保存什么 | 接续方式 |
|---|---|---|
| 项目持久材料 | 目标、决定、任务、pin、启用哪些可选能力、指定合入去向 | 优先复用项目已有 AGENTS / lock / 任务文件，随仓库或宿主任务包传递；需要的新增字段采用可选方式 |
| 环境内运行事实 | 实际 session/host、启动回执、心跳、执行与释放状态 | 同一个本地 clone 使用 common git dir；同一远程工作区也使用自己的共享目录；不把本机 PID 或 running 标记复制成云端活跃证明 |
| 跨环境任务回执 | task id、源 commit、修改范围、结果 commit/PR、验证与待处理项 | 先复用代码仓库、PR 队列和宿主已有结果渠道；接收端核验后更新本地记录，不同步全量聊天或循环覆盖各环境的运行文件 |

“文件优先”提供耐久材料，不等于不同机器实时共享同一个文件系统。Git 版本同步能送规则和任务，不能充当活进程检测、实时消息总线或跨机器互斥锁。

## 5. 各场景的目标行为

| 场景 | 入口应该做什么 | 用户操作 |
|---|---|---|
| Claude → Codex，同机同 clone | 找共同账本，读取现有角色与当前任务，登记当前真实会话；接线缺失就明确提示 | 不重启一套角色；宿主首次安装/信任正常完成 |
| linked worktree | 读取同一 common dir；自己的执行身份与共享角色分开 | 不重新初始化项目，不因缺 claim 阻止普通工作 |
| 应用重启或原窗口 compact | 重读项目与真实回执；活跃角色复用，已明确关闭的角色按既有启用授权恢复 | 不因 compact 或重启重复开树；未知状态先核实 |
| 同机另一个 clone | 识别不同工作区，载入相同项目配置；不靠 remote URL 合并两个 .git 的运行权 | 可复用规则；是否共享协调方须有明确接入去向 |
| 持久远程工作区 | 自动载入项目配置，在该环境登记执行身份，通过回执渠道接入项目合流 | 配置环境一次，后续会话自动接续 |
| 厂商托管云任务 | 从任务可见的仓库/任务包读规则和 pin，以执行角色接单，回传结果给项目指定合入方 | 不要求每个云任务另开值守；适配与回传需实际完成接线 |
| 无法读取项目文件或连接回执渠道 | 显示未接入/待连接及真实缺口，不冒报同步、有人值守或任务已交付 | 提供明确恢复路径；普通非协调工作按现行规则判断 |

一期建议将值守/合入入口放在一个持久本机或持久远程工作区。临时云任务承担执行，交回分支/PR与证据；使用现有队列，不在每个云容器复制一个同级值守。云端不能因自己的 .git 没有本机登记就推断项目全局没有负责人。

如果用户以后要求本机和多个云环境都能争取值守权，则必须有共享的原子认领依据及旧持有者失效机制。仅靠各环境的 markdown 或时间戳不足；这一要求不能用本草案偷换成本地已支持。当前三权与 fail-open 的可执行政策仍保持原样，跨环境合入判定须单独验收。

## 6. 开发切片与验收

1. **统一状态与会话挂接，P0**：复用已有状态命令的数据，生成一份简短真实结论；支持各宿主启动、恢复和必要的压缩续跑接线。状态查询只读。验收为 Claude/Codex 同项目报告同一任务和负责人，并区分未启用、未接入、已准备、活跃、失联/未知。
2. **真实身份与复用，P0**：记录 host + 实际 session id + 工作区身份，角色归属核到具体会话；项目内单角色的创建/续接互斥。验收为同目录两个窗口不同时获得值守身份、不同 host 不重复造 patrol，未知/迟到事件不覆盖新持有者。
3. **可携带配置与云启动入口，P0/P1**：项目材料不依赖个人主目录、symlink 或硬编码绝对路径；使用实际环境支持的初始化机制。验收为新远程工作区自动识别 pin、任务和指定合入去向；环境重建可重复执行，失败项如实显示。
4. **最小跨环境回执，P1**：统一 task id 与结果指针，关联已有 PR/宿主回执；按现行权限运输，来源与合入授权分开。验收为一项云端执行结果实际回到唯一合入入口，重发不重复派工，较旧回执不覆盖新任务状态；离线有可恢复材料但不假冒 live。
5. **接回成长闭环**：把缺 hook、重复角色、遗漏交单和重复确认作为真实摩擦案例；修正后的本机/远程任务分别回访。复用既有 intake/bench，不另建常驻模型循环。

默认目标是减少重复操作。宿主首次登录、hook 信任、云环境发布仍遵守提供商正常流程；环境运行时自动执行已配置的接入件，不把它变成人每开一个窗口都要重复的仪式。

## 7. 官方能力依据与边界

- [Codex hooks](https://learn.chatgpt.com/docs/hooks)：有 SessionStart、UserPromptSubmit 等生命周期事件，支持额外上下文；项目 hook 依赖正常信任。这里只证明有接入接口，本机实际接线仍以上表为准。
- [Codex 当前云环境](https://learn.chatgpt.com/docs/environments/cloud-environments)：支持保存环境安装/启动配置；已有任务保留自身状态，新任务使用已发布环境。仓库中的 skill 可用于云任务，本机个人 skill 不自动同步。因此不能把本机 Agent-On symlink 当云端已安装证明。
- [Claude Code 云端](https://code.claude.com/docs/en/claude-code-on-the-web)：常规 cloud 启动由 VM clone 远端分支，不直接使用本地 checkout；Remote Control 操控本机与真正云任务是两种场景。云环境过期后重建不会恢复原后台进程。因而需要携带文件与实际接续证据。

本轮只保存评审和方案；没有接入云账号、发布云环境、启动值守/巡逻、发送跨窗口消息或修改执行政策。具体字段、云环境类型及回执适配接口仍需在开发切片中按实际宿主确认。
