## 1. 用户这次明确的定位

用户指出：最初并不是要做成 Superpowers、GSD 等同类执行框架；核心应当是“可以消化、可以自己迭代成长”。同时要求重新审视限制、执行速度、助手合流与模型进化后的脚手架价值。

据此，建议产品表述收敛为：**把真实项目中的经验变成可验证、可复用、可撤回的方法，并让后续项目少踩坑、少办手续。**

这延续 CHARTER 的“越用越强”与“不做编排运行时”。具体默认行为与权限调整是下文的提议，不能把定位确认当成所有删改都已批准。

## 2. 核心保留五件事

| 核心 | 用户获得什么 | 最小形态 |
|---|---|---|
| 项目上下文持久化 | 换工具、模型、会话后能接着干 | 目标、当前工作、明确禁区；复用已有状态文件，避免重造清单 |
| 经验采集与回流 | 一次踩坑能帮助下一个项目 | 项目里一条带证据的记录，回流到 intake；原始材料与正式方法分开 |
| 消化与淘汰 | 根据归因选择改方法、减方法或保留案例 | 采纳 / 拒绝 / 缓议有理由；采纳的动作可为修正、合并、降权、删除或新增 |
| 验证与授权边界 | 完成可信，钱、数据、权限和别人的成果有保护 | 与任务风险相称的验证；不可逆或未授权动作明确停下 |
| 版本化供货与安全升级 | 知道正在用什么，能获得改进且不丢本地定制 | 可追溯版本、改动摘要、迁移差异；核对规则和实际执行的 hook / CLI |

契约、worktree、单一状态写者、独立审查仍有价值，但分别由真实接口协作、并行写入、共享状态、高风险触发，不是所有项目的默认装备。单写者约束针对具体共享状态，不等于所有开发或沟通都交给一个窗口。

## 3. 成长应包含减法

现有闭环已有拒绝、缓议、回滚与 local_deviations；问题在于两条相反的硬要求仍在推着规则增长：

- `boot/settlement.md` 与 `playbook/iteration-loop.md`：同类问题跨两个项目出现即强制升 L3。
- `playbook/meta-principles.md` 与消化收尾：每次复盘 / 消化必须改方法正文才算成功。

建议调整为：

1. 先归因：业务问题、环境问题、执行错误、模型能力不足，还是脚手架自身制造的摩擦。
2. 重复出现只提高处理优先级；是否变成通用规则，还要看适用条件与最小有效解法。
3. 一次消化可以只拒绝、合并、保留案例或撤销旧规则，不为完成指标制造新禁令；处理结论仍留痕。
4. 规则变更在后续相关任务中核验效果；已有经验继续回流，不再新造一套运行台账。
5. 实际收益不够就缩小适用范围、退出默认或回撤。原始证据保留在案例 / 历史层。

“自己成长”指 AI 可以完成归因、拟改动、验证与授权范围内的落地；改变产品方向、扩自己的权限、未授权外部操作仍有明确责任人。

## 5. 助手如何合：分清两段，交付链尽量短

用户随后补充：值守已存在且目前运行尚可，主要痛点是多个页面窗口各开 worktree，临到合并才发现共享改动冲突，同时重复消耗 rebase、CI 与 TDD。要求保留值守、设计前置巡逻与统一调和，并另议跨模型调度。具体方案见同日 [巡逻与跨模型调度设计](2026-10-01-patrol-coordination-and-model-dispatch.md)。

进一步补充包括：自动创建独立巡逻/任务记录窗口，以及定期释放无用 worktree 的“清道夫”。清道夫建议为后台作业，在巡逻窗口呈现；复用现有 GC 分类，补结束/占用、ignored 内容、执行前复核与恢复依据后，在明确纳管范围自动回收。现行“GC 只报告”尚未修改，本轮未执行回收或开启定时任务。

| 执行者 | 交付物 | 收口责任 |
|---|---|---|
| 同一任务的子助手 | 改动 / 自己树里的 commit、验证结果、剩余问题 | 派出它的主助手核验并集成，必要时在主助手自己的树应用提交；不得把这解释为可跨树 add/commit |
| 独立功能会话 | 自己分支上的 PR；未完成复核用 draft | 作者修业务与语义冲突；PR ready 后交给合入负责人 |
| 合入负责人 | 对最新 head 的政策判定与验证、合并、审计记录 | 同刻一个负责人改主线；值守在班用值守，不在班按维护者规则；合完记录与回执 |

建议常规合入流程收敛成：**ready PR → 核验最新 head 与政策 → 授权内合入 → 记一行审计、回执结果**。base/head 改变后验证对应的新状态；检查为空不能当作通过。真冲突退给作者，其余机械工作由既有工具处理。

发现的具体混乱应先修正：

- `docs/babysit.md` §2 仍说 canonical 基本都“必须先问”，§3 已改为穷举硬停例外、其余默认自动合；前者应按后者与 `policy.json` 对齐。
- CONTRIBUTING 的交单入口仍先读分支内“交接快照”，而同页已有 `oncall status`；机器寻址应只认当前登记。
- “子代理不 push”与“独立功能会话可 push 自己分支”是两种对象，模板须标清适用对象。
- `record` / `report` 应显式使用同一份账本；不能因脚本在哪棵树而默默换账本。现行手册已记录两棵树报出不同审计结论的事故。

按用户最新补充保留值守与现行三权归属。多窗口时建议由值守兼任用户的总控入口；巡逻/任务记录默认自动创建并展示为独立会话，用户仍在主窗口说话。记录窗口自动收需求与回执、维护简短任务清单，在派工前及实际改动出现时提供冲突证据与调整建议。本窗口内部的小修改可以直接沟通；跨窗口、共享改动与合流仍由值守调度。此前关于缩小值守通信范围的提议不作为本轮实施方向。

可用 GitHub 原生 auto-merge 承担满足 required reviews/checks 后的等待与合入；复杂队列若满足资格和 CI 接线可用 merge queue。两者不替代本仓硬停分类与独立审计，也不需要自建编排运行时。

- [GitHub auto-merge](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request)
- [GitHub merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)：资格限相应组织仓，required CI 要支持 `merge_group`；本轮没有核本仓当前 GitHub 设置，不能假定已经可用。

## 7. 落地顺序与验收

1. **先对齐现有拍板**：清 lane 前置残留、值守旧审批句与错误寻址；这批主要修执行入口的漂移。
2. **精简默认体验与消化判据**：自动续接、任务级装备、按风险验证、短报告、允许消化做减法；同步正文与模板。
3. **再改机械闸与升级执行面**：提交范围判据、明确账本位置、构建身份与升级回执；先有真实反例再改代码。

验收看实际任务：

- 明确的“继续做 X”能开始，不再索要同一决定的第二次确认。
- 普通小改动不用先补全产品文档 / 仪表盘；高风险改动仍得到对应验证。
- 未登记但已隔离的 worktree 不因登记而停。
- 不提交的重叠文件不会把无关提交或推送锁住；跨树篡改与未授权动作仍受保护。
- 一批经验全部拒绝 / 合并 / 保留案例时可以有完整处理结果，不为凑成果新增规则。
- 同一 PR 在入口文档与机器政策里得到相同的审批分类；合并记录可核、真实冲突有作者接回。
- 升级回执能分清“规则文件已更新”与“实际二进制已更新”。

用现有任务记录比较确认次数、误拦次数、交单到合入时间、返工与高风险遗漏；没有数据的项标未测，不预报提速比例。日常状态源保持少而明确，不为本次评审再加运行台账。
