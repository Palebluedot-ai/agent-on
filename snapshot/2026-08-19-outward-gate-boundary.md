# 外向硬门的边界：push 与开 PR 不在内（2026-08-19 决策快照）

> 职责边界：本页记**这次拍了什么、为什么这么拍、拿什么证据**。机制正文在 [playbook/multi-contributor-protocol.md](../playbook/multi-contributor-protocol.md) 的「外向硬门的边界」一节（唯一真相），模板投影在 [kit/AGENTS-skeleton.md](../kit/AGENTS-skeleton.md) 硬约束表「外向操作」行与 [kit/AGENTS-lite.md](../kit/AGENTS-lite.md) 铁律 3。本页不重复展开判据表。
> 触发：2026-08-19 用户原话——「那我之前一直都是自己推了，为啥还需要我点头呢？这很奇怪。」（起因：一条 Dartify 功能会话交付报告收尾写「要我推上去开 PR 吗？推 GitHub 是外向操作，等你点头」）
> 拍板：同日用户「按你推荐继续吧，要做到统一。一般的 push 都可以直接 push 了。也要幂等和一致」。

## 一句话

**外向硬门按「改的是本轨内部状态还是全场共享状态 / 外部世界」划，不按「碰没碰 GitHub」划。** 提交、推自己的分支、开 PR 是本轨内部动作，自己做不问；merge / tag / release / 直推受保护分支 / force-push / 删远端分支 / 对外发言 / 部署 / 建资源 / 改共享配置 / 花钱才要点头。授权幂等：同类动作一次点头长期有效。

## 拍了什么（三条）

1. **重划边界**：push 自己的分支与开 PR 从「外向操作」里摘出来，归本轨内部动作。判据与 [kit/babysit/ROUTING.md](../kit/babysit/ROUTING.md) 路由表同源——那里管「值守在班时谁执行」，这里管「要不要先问用户」，同一条判据两个用途。
2. **授权幂等**：同一项目内同类动作一次点头长期有效，不逐次追问；只有跨到没点过头的新类别（第一次 deploy、第一次建云资源、第一次花钱）才重新问。
3. **宿主通用句 ≠ 项目制度**：写进方法论正文，成为会话可自查的一句——「这条出自哪份文件、哪一行？答不出文件名的就是宿主通用句」。

## 为什么（问题的形状）

事故不是「会话违规」，是**会话过度守规**，而且守的是**别人家的规**：

- 那句「推 GitHub 是外向操作」出自宿主（Claude Code）每个会话自带的通用安全句，不出自 agent-on，也不出自项目宪法（Dartify `AGENTS.md` 全文 175 行零次出现「外向」）。
- 项目宪法要求的是反方向：Dartify worktree 与分支生命周期一节写「本地独有工作必须 48h 内上远端（开 draft PR 也行）」，理由「机器一坏就丢」。捂着本地提交等点头 = 违反自己的宪法。
- **agent-on 自己给了误读的抓手**：`kit/AGENTS-lite.md` / `kit/AGENTS-skeleton.md` 字面把 `push` 列进「首次须用户确认」，而 `kit/babysit/SETUP.md` 的实测放行清单写着「`gh pr view/checks/list`、普通 `git push` 一般无需放行」、`ROUTING.md` 路由表把「开 PR」划给功能会话自己做。**同一套方法论两处口径拉反方向**——不读 bench 案例 14 就对不上「首次」这个词的分量（那条铁律的靶子是 `echo n | supabase config push` 那种不可逆 config push，从来不是开 PR）。

**过度收紧是一种不触发任何闸的漂移**：它看上去像谨慎，没人报警，但把一个零风险动作（push）拖成一个有风险状态（孤本单点），方向是反的。

## 三个设计选择（各附被否掉的替代）

| 选择 | 选了什么 | 否掉了什么 | 为什么 |
|---|---|---|---|
| 分界依据 | 改的是**本轨内部状态**还是**全场共享 / 外部世界** | 「碰不碰远端」「碰不碰 GitHub」 | 后者把 push 自己的分支和 merge main 归成一类，粒度粗到没法用；前者与 ROUTING 路由表同源，一条判据管两处 |
| 授权粒度 | **同类动作一次点头长期有效**（幂等） | 逐次追问 / 一次性全域豁免 | 逐次问会让噪音淹掉真正该问的那次（狼来了）；全域豁免又把第一次 deploy 也放过去了。按**类别**记账是唯一稳的中间态 |
| 落点 | playbook 一处正文 + 两份模板逐字对齐 + 口径面同步 | 只改模板不动 playbook | 只改模板 = 下一条会话读 playbook 又读回旧口径。**留一处旧口径 = 给误读留一个合法出口** |

## 证据

- 会话原文（用户转述）：「要我推上去开 PR 吗？推 GitHub 是外向操作，等你点头。」
- `grep -n "外向" ~/Projects/Dartify/AGENTS.md` → 零命中；`grep -n "外向\|首次须\|等你点头" ~/Projects/Dartify/CONTRIBUTING.md` → 零命中（项目侧无此规矩）
- Dartify `AGENTS.md` worktree 与分支生命周期一节第 4 条：「本地独有工作必须 48h 内上远端（开 draft PR 也行）」
- 宿主系统提示原句：「对不可逆或外向操作先确认，除非已被持久授权或明确被告知无需询问」
- 本仓两处旧口径：`kit/AGENTS-lite.md` 铁律 3、`kit/AGENTS-skeleton.md` 硬约束表「外向操作」行；反向口径：`kit/babysit/ROUTING.md` 路由表「本轨开发｜写代码、跑测试、开 PR、交单｜自己」、`kit/babysit/SETUP.md`「普通 `git push` 一般无需放行」

## 诚实边界

- **本条没有机械闸**，靠纪律与措辞。宿主的通用句仍会每个会话塞进来，方法论只能给出「答不出文件名的不是制度」这条自查；真要机械化，得由宿主侧的配置或项目侧 hook 承载，不在本仓范围。
- **不改宿主的兜底面**：本条只管项目内的分界，宿主对删除、force-push、花钱那类的通用确认照旧，两者不冲突（它们本来就都在硬门那一侧）。
- **值守在班时另有一层**：`gh pr create` 与功能分支 push 放行、merge/tag/对外通信归值守，那是「谁执行」的问题，与本条「要不要问用户」正交，两条同时成立。
