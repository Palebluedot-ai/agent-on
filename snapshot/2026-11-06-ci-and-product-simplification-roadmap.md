# 2026-11-06 · CI 提速与多 agent／多面板退场路线图

> 职责边界：本轮开发／设计路线图，记录用户确认的删除范围、线上基线、实施顺序和验收。本文是后续开发依据，不宣称功能已删除、CI 已提速或本机已卸载；当前产品规则仍以现行正文与代码为准。

## 1. 用户目标与已确认范围

用户要求：这个库 CI 排队太慢，从 Agent-On 角度一起优化；此前多 agent、多面板没有达到预期，删除冗余功能，先生成路线图。

2026-11-06 用户进一步确认：**删除 Agent-On 自建的派工、巡逻、活动采集和网页面板；保留普通对话、文字状态、Git 冲突保护及合入审计。**

产品收缩到：在当前对话里接住目标，读取项目事实，完成修改与必要验证，按已有权限交付，并给出结果和下一步。用户不必管理角色、窗口登记、活动状态或第二套任务台账。

宿主原生能力仍由用户按需使用；Agent-On 不再包装一层跨宿主启动、模型诊断、任务回传和面板展示系统。合入所需的现行身份／权限检查和独立审计保留，不要求为普通单会话任务另开值守窗口。

### 2.3 夜间延迟发生在运行创建之前

配置是 UTC `17:23`，即香港次日 `01:23`；近期实例：

| 香港日期 | 计划触发 | 实际 run 创建 | 延迟 |
|---|---|---|---|
| 11-04 | 01:23 | 06:22:07 | 4 小时 59 分 07 秒 |
| 11-05 | 01:23 | 06:40:46 | 5 小时 17 分 46 秒 |
| 11-06 | 01:23 | 06:42:08 | 5 小时 19 分 08 秒 |

最新 job 创建后 2 秒取得 runner。因此不能把这五小时称为 Rust 测试慢，也不能靠删测试解决。GitHub 官方说明 schedule 在高负载时可能延迟；本次可以定位到触发阶段，尚不能证明 GitHub 内部的具体原因。[官方 schedule 说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

默认处理：夜间回归作为异步兜底，PR 交付不等夜间；展示最近一次真实成功时间，不把计划时间写成完成时间。保留现有手动全量入口用于有需要的补跑。若将来要求固定时刻前完成，再单独选择已有外部可靠调度；本轮不新增常驻调度服务，也不靠频繁定时触发增加排队。

## 3. 目标使用体验

| 用户动作 | Agent-On 应做的事 | 可见结果 |
|---|---|---|
| 在当前对话给目标 | 读取现有规则、代码、任务与授权；就地推进 | 结果、证据、实际卡点 |
| 询问当前进展 | 读取当前项目文件、Git 与已有 PR 证据 | 一段文字：目标、已完成、未完成、下一步；取不到的明确未知 |
| 提交一批成果 | 本地验证相关范围，CI 给出当前候选结果 | 等待原因明确到触发、runner、检查或合入条件 |
| 请求交付 | 按已有权限合入、独立记账、依仓库规则发布 | 明确已实现／已验证／已合入／已发布到哪一步 |

默认无需网页、端口、活动观察器、系统进程扫描、自动开窗或跨模型派工。文字状态从项目已有事实读取，不把被删的任务系统换个名字重建。目标无法从项目记录获得时直说；临时对话上下文继续由宿主管理。

## 4. 删除／保留清单

| 对象 | 处理 | 主要落点与注意事项 |
|---|---|---|
| 项目网页面板、系统总览 | 删除服务、HTML、轮询、浏览器专用测试和入口 | `cli/src/dashboard.rs`、`dashboard.html`、`system_dashboard.rs`、`system_dashboard.html`；`dashboard`、`status --serve/--system`、面板型 `agent report` 退场 |
| 自建派工与巡逻 | 删除启动器、Terminal/tmux/桌面桥接、重试／续接／阶段交接及自动回传 | `coordination.rs` 中 dispatch/patrol 执行部分；`dispatch`／`agent-os`／`patrol` 和相关入口退场 |
| 活动采集 | 删除逐工具事件记录与活动投影 | `activity.rs`、`activity` 命令、对应 capture hook；SessionStart 身份接续独立保留必要部分 |
| 自建任务运行台账 | 停止新增和依赖，旧记录只作迁移／历史参考 | `task` 的派工配套状态机退场；使用项目已有任务／文档，不新造另一套持久任务协议 |
| 自建模型兼容诊断 | 随跨宿主启动能力退场 | `codex_model.rs`、`model-check` 及专用测试；不影响用户直接使用宿主模型 |
| 派工配套清道夫 | 随受管派工 checkout 生命周期退场 | `janitor.rs` 及专用调度；保全现有 worktree、分支、未提交文件、恢复 ref 与回执，不自动删除用户资产 |
| 文字 status | 保留并解除面板／巡逻依赖 | 独立参数类型，来源为 Git、现有项目记录及合入事实；保留有用的 `--json`，明确字段迁移 |
| Git／跨仓保护、会话身份 | 保留 | guard、prepush、worktree 的实际冲突检查；session 的身份解析不能随 capture 整体误删 |
| 合入与审计 | 保留，压缩多窗口说明 | master、landing、oncall 的必要合入身份／权限、`tools/merge-audit/`；不新增值守常驻窗口 |
| 初始化、续接、经验回流、版本发布 | 保留 | setup、doctor、boot、settle/digest、tag-release；正文与入口去除已退场依赖 |

已确认的技术耦合：`status` 使用 `DashboardArgs`；`project_status` 读取 coordination/activity；session 读取 coordination::Store；oncall/master 使用 coordination 中的锁与原子写入。这决定了**必须先抽出少量共享基础，再删大模块**，不能直接整文件删除后放松保护来修编译。

共享基础只保留路径、锁、原子写入和必要身份等现有能力；不借拆分新建框架、事件总线或通用运行时。

## 5. 开发路线：按可验收批次串行推进

| 阶段 | 工作与交付 | 验收出口 |
|---|---|---|
| P0 · 对齐基线 | 实施前重新核 main/本地差异，接上 #44；记录同类 PR、夜间 job、缓存、编译与测试耗时；列出本机已安装的旧 hook／调度／执行器 | 不覆盖并发工作，不重复实现 #44；证据区分触发延迟、runner 等待、执行耗时和合入等待 |
| P1 · 修 CI 的真实浪费 | 核实缓存失效原因，明确 Rust 工具链版本（满足 1.89+）；调整 key 和保存策略，使依赖与构建结果在兼容环境复用；保留当前按范围验证及必需检查名 | 同工具链／同输入连续运行能复用依赖，不再每日命中旧缓存后重编整批依赖；冷缓存仍正常通过 |
| P2 · 拆开文字状态与运行系统 | status 独立参数／采集；抽出 oncall/master/session 必需的文件锁、写入与身份逻辑；入口和正文切到当前对话的交付路径 | 无 coordination 活动台账也能报告 Git／合入事实；保留真实冲突、身份和审计回归；坏历史记录不锁住普通工作 |
| P3 · 真正删除失败功能 | 删除两套面板、自建派工／巡逻／活动／模型诊断／配套任务及 janitor 执行面；删专属测试和 CI 映射；准备旧安装迁移 | 不编译被删模块，不启动服务／开窗／逐工具采集；保留行为仍有测试；旧资产可找回 |
| P4 · 文档与真实交付验收 | 更新 playbook/kit、skill/Codex 入口、README/AGENTS、安装说明；验证新装和旧版升级；完成发布及实际执行器核对 | 一个普通任务从当前对话到交付跑通；不用面板／派工台账；完整回归一次通过；拿真实 CI 比较前后效果 |

依赖顺序：P0 → P1 → P2 → P3 → P4。每阶段按可 review 的变更组织；不为了这份计划再拆多个 agent 或面板。P1 的缓存优化先拿真实收益，P3 的产品删除进一步降低编译和测试成本。

### P1 的实施约束

- 先量再改：分别检查 Cargo 失效指纹、编译器变化、构建 profile、构建身份脚本与缓存保存回执。clippy 与 test 不同模式有合理编译差异，不以“零编译”作不可能承诺。
- 候选方案：依赖下载缓存与构建缓存分开；key 包含实际工具链、平台、锁文件与构建配置，构建缓存增加可更新的内容标识，并用兼容前缀恢复。限制写入频率与容量，避免每次提交永久堆积。主分支可信缓存与 PR 缓存遵循 GitHub 的作用域规则。
- 固定工具链不能替代最低支持版本承诺；如日常工具链高于 1.89，发布前另验证声明的最低版本，或显式调整声明。
- 现有 PR 并发取消和“无合入后重复 push CI”已存在，保留即可，不列为新增优化。
- 暂不增加 Rust 测试矩阵、更多 runner 或新缓存服务；额外并行需要先证明足以覆盖重复启动／编译成本。
- 两个必需检查名保持稳定，无关步骤明确跳过；缺结果、失败或取消不得被汇总成成功。风险模块／未知影响范围仍扩大验证。
- 夜间延迟单独计量；不承诺靠换缓存、runner 或 cron 分钟能消除 schedule 延迟。

GitHub 缓存不可原地修改已有 key，新增内容需要新的 key；选型依据：[官方缓存说明](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)。

### P3 的迁移与删除顺序

1. 先列明实际安装的 Agent-On hook、调度、受管 checkout 与历史记录，记录归属和回退方法。
2. 停止旧功能的 Agent-On 专属采集／巡逻／清道夫调度；保留必要 Git guard、会话身份及其他工具 hook。不能只改仓内文件就报告已卸载。
3. 拆除源码、路由、插件声明和文档入口；将历史执行书归档为明确的历史材料，修复引用。历史快照与发布账本不改写为“从未有过”。
4. 被移除命令如需一个过渡版本，只提供轻量退场提示，不保留旧实现；明确过渡期限。旧 status JSON 消费者与安装脚本列出替代方式。
5. 旧 task／activity 记录留作只读历史，不参与新状态决策；不把陈旧记录误报成正在工作。现存 checkout 不随功能退场删除。
6. 验证卸载／升级可重复执行，执行中断可继续；只清理可确认属于退场功能的安装项。实际宿主执行器与插件需核 `build-info`，不能用缓存目录名代替版本。

## 6. 验收标准与目标

以下是目标，不是已实现的承诺。时间比较使用相近 runner／工具链／缓存条件，至少三次可比样本报告中位数和范围；P95 留到样本足够后再统计。

| 维度 | 验收 |
|---|---|
| 普通使用 | 单一对话可以完成一个代表性任务；无需自建派工、巡逻、网页或活动采集 |
| 删除完整性 | 活跃入口和构建中无退场功能；专属测试随行为删除；共享安全测试先迁移后保留；历史引用明确标注退场 |
| 文字状态 | 不启动后台、不扫描全机项目；无数据明确未知；当前项目 Git／交付事实可读；不虚报其他窗口正在做什么 |
| PR 文档路径 | 不恢复 Cargo 缓存、不编译 Rust、不跑 Rust 测试；两个必需结果均到达 |
| 缓存 | 兼容输入的第二次运行复用依赖构建；环境或锁文件变化正确失效；保存回执与预期一致 |
| CI 执行耗时 | 以最新全量 CLI job 81 秒为参照，缓存热且精简完成后，争取中位数 ≤ 60 秒；未达则报告剩余成本，不通过漏测达标 |
| 夜间调度 | 明确计划时间与实际成功时间；交付不等待夜间；当前数小时触发延迟持续如实展示，不能伪称已修复 |
| 安全与交付 | 真同文件冲突、跨仓边界、会话身份、必需 CI、合入审计与中断恢复继续有效；旧 lane／台账不新增误拦 |
| 升级 | 新装和从 v0.29.0 升级均实测；旧功能不再由安装残留触发；用户文件、分支与历史回执保全 |

开发中验证受影响范围；P2/P3 的共享基础修改执行相关完整回归；删除完成后批次跑一次完整 Rust、审计、CI 选择器、文档与安装验证。无需反复为同一输入重跑完整审查。

## 7. Agent-On 方法回流与发布

- 本轮经验落到 `playbook/delivery.md` 与 `kit/delivery-workflow.md`：当前对话交付、复用已有项目事实、验证按影响范围、区分四类等待。同步 `boot/session-handshake.md`、`skill/SKILL.md`、`codex/prompts/agent-on.md`，不只改 README。
- `kit/live-control-plane.md`、`kit/patrol-control-plane.md` 的失效内容归档；`kit/session-control-plane.md` 保留必要身份和续接约定。核对 CHARTER 中可选巡逻／派工／清道夫描述，准备与已确认删除方向一致的修订。
- 公共命令和 JSON 字段删除可能构成 breaking。按仓库“**不动手会坏 = major**”判断，附迁移注记；不为了保持 v0.x 将破坏性删除伪装成 patch。
- v1.0 另有“外人使用与反馈回流”的既定验收，不能因删功能就声称达成。实际版本号需在迁移方案定稿时对齐这一约定；本路线图不预定 v1.0 或谎报产品成熟。
- 实施后 decision / refactor / docs / chore 分层；正式交付遵守本仓当前合入政策、CHANGELOG、README/AGENTS pin、annotated tag 与 push 纪律，一批发布时 tag 钉在交付 HEAD。发布与本机安装分别取证。

## 8. 尚未证实的事项

- 用户曾感受到的特定长时间 PR 排队，当前样本未复现；实施期间遇到时记录对应 run 和 job 时间，不能与夜间延迟混算。
- 缓存失效的精确原因和最优 key 尚未做对照实验；现有证据只证明命中后重编、未更新缓存。
- 本机／其他项目的旧调度与插件残留尚未盘点，不能仅凭源码推断已启用或已卸载。
- 版本号、过渡提示期限、status JSON 迁移细节在 P2/P3 定稿；用户已确认功能删除范围，无需反复询问同一范围。

本轮交付仅为这份路线图；产品代码、远端配置和本机安装尚未变更。
