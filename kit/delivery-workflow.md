# 交付入口：把目标推进到可验收成果

> 职责边界：供 `/agent-on deliver`、`$agent-on deliver` 或中文“agent-on 交付”执行；适用于接入 Agent-On 的项目，不是本仓专用 CI。检查节奏唯一约定见 [功能交付](../playbook/delivery.md)。本入口协调已有工具、窗口与状态，不启动通用编排引擎。

## 1. 续接目标

读取当前用户目标、项目规则、已有任务与实际改动；先保护已有未提交工作。运行 `agent-on status --json` 共读任务、窗口、值守和本地 PR 证据。执行器缺该命令时读取现有 task/landing/Git 信息，并注明版本缺口；不开网页也能工作。

复用已有验收；需要补充时从用户对话和代码草拟，只问无法推断且会改变结果的事项。目标明确就继续，不要求用户先选内部角色、补全大规格或逐个指定 skill。没有 lock 的现有项目也可读状态与交付明确目标；要求正式接入时再按 adopt 补必要映射。

完成条件：当前批次的结果、范围、依赖和验收清楚，工作区中已有修改的归属已辨认。

## 2. 分工并推进

单窗口可完成就直接执行。确有并行需要时先收拢共享修改，再按 [派工模板](track-prompt-template.md) 把独立工作包交到已有授权的窗口；值守在班时由值守中转。任务 id 沿用项目现有编号，已登记的不重复 add。

需要本机共读回执时使用已有命令：

```sh
agent-on task add <id> --goal "可交付结果；验收见现有任务位置" --path <负责范围>
agent-on task progress <id> --state working --note "当前进展或下一步"
agent-on status
```

消费者登记时用 `--depends-on <前置任务id>`，运行前核实际合入证据。`task add` 只是登记意图，不会启动窗口或认领独占权；实际派工沿 [现有执行书](patrol-control-plane.md)。创建聊天、换模型或改派须符合已有用户指派，不能从一张图自行推导授权。

完成条件：每个执行窗口知道自己的目标、共享修改归属、前置条件与证据位置。用户不负责逐窗口重述上下文。

## 3. 验证本批成果

依 [功能交付](../playbook/delivery.md) 选择相关检查与一次批次审查。模型、工具或窗口切换不自动触发全流程重跑；只复查本批受影响行为。需求中途改变时更新原验收，明确作废旧要求。

Matt 可用于代码设计、诊断和工作包定义；已装且明确调用时遵其约定与本项目范围。同一阶段不叠加 Matt、GStack 和 kit 三套 review。没有这些插件就用主会话与 [审查模板](review-prompt-template.md)；不为了交付先安装技能。

需要调整项目 CI 时：先读取真实检查、分支保护与部署触发，识别必需检查、夜间回归和每周复盘，按当前授权修改配置。required 汇总必须得到明确结果；纯文档不跑无关平台，检查器或共享基础变化扩大相关验证。现有保护未改变前继续满足它。夜间与周检复用既有 CI/宿主调度并验证真实回执，不能只写一句“每周”就报已落地。

完成条件：本批需求与相关必要验证有实际证据；未验证项与非阻塞建议明确分开；没有新证据就结束该轮检查。

## 4. 交单并收口

结果直接引用已有检查输出、提交、PR 和需求来源，不抄写全套报告。需要本机结果回执时：

```sh
agent-on task result <id> --file <已有结果文件>
```

回执到达只表示待验收，不表示已合入。按 [合流检查](merge-checklist.md) 处理相关条件；值守在班按 [交单约定](babysit/CONTRIBUTING-CLAUSE.md) 发一次交单，接收地址从实际登记读取。未完成必须的审查时 PR 保持 draft。

值守或无人在班时的维护者按 [交付统筹](master-delivery.md) 运行 `agent-on master --apply`，串行合入已授权且就绪的 PR。WAIT 留到下一轮，FIX 沿已有授权处理；合后自动记账，中断先恢复回执。已有批准不重复索取。

合入与发布仍分开取证；满足现有授权与条件即可继续，无需再等夜间全量或周检。确认任务收口且执行会话已退出后，才按既有规则带证据 release。原窗口回报结果、验证、交付位置和剩余阻塞；普通成功无需追加复盘任务。

完成条件：结果能被下一个窗口或用户实际使用，交付到了哪一步有真实证据，下一步有明确负责人。
