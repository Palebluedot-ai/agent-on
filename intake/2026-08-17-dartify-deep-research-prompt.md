### deep-research-prompt-template（深度调研类派工的可复用 prompt + 四条执行纪律）

- source:Dartify @ 6811ab1 | pin v0.9.1
- evidence:一次真实的 Deep Research 派工（桌面端选型 + 团队权限 + Goal 服务），5 路并行外部调研 + 仓内审计，产出 `docs/architecture/desktop-team-plan.md` 1457 行（PR #180 已合）。交付前做了一轮对抗式核验：**158 条仓内可验证断言 → 120 条确认 / 38 条改正**，其中两条硬伤——
  ① 文档贴了一条**假的命令输出**（`grep -rin "create policy" supabase/ # → 0 命中`，真实 4 命中）。成因是先用大写搜了一次得 0，改小写重搜时带 `| head` 被截断，把截断当全貌；
  ② 一个**无出处的数字**（「42 个端点」）还配了一句**编造的解释**（「带 `:id` 的会被正则截断」）——那条命令实际输出 50 行、去重 29 条，且正则根本不会截断。
  另有 7 条结论在调研中被翻转，最大一条是「prompt 假设用 RLS + membership 做权限」在该仓不成立（该仓 28/31 表零 policy，授权 100% 在网关）——**这条发现来自 `grep`，不来自任何一篇外部文档**。
- confidence:high（工件已实跑一轮并产出已合并交付物；四条纪律各自对应一次可指认的失败）
- claim:深度调研类派工存在四个**结构性**失效点，靠事后核验补救成本高且不可靠，应当烧进 prompt 模板：
  1. **仓内审计必须先于外部调研**——外部资料只能回答「业界怎么做」，只有仓内审计能回答「这题在这个仓是什么形状」。顺序颠倒时，最关键的发现会在做到一半才撞上，前面的推导要返工。
  2. **必须显式授权 agent 推翻派工人的技术前提**——派工人的前提是假设不是事实；不授权时 agent 会为迎合前提而硬套（本次前提确实错了）。
  3. **数字纪律要写到「禁止为数字编造解释」这一层**——只写「数字要有来源」拦不住失效②：给数字配一个听起来合理的解释**比不配更危险**，它让读者以为你核过了。同族还有：引用命令输出必须是真实输出，用过 head/tail 截断的必须确认结论对全集仍成立。
  4. **自核验是交付的一部分不是可选项**——且必须是**对抗式**（默认自己写错、目标是找错），判错的再做独立复核避免冤枉。本次没这一步，那两条硬伤会带着交付。
  附带第五条（较弱）：交付物要**区分「方案」与「决定」**，单列待拍板项，别把产品决策伪装成技术结论。

### 原版（v1 · 领域可替换）

```text
【Goal / Deep Research Prompt】

角色
你是一位拥有 10+ 年经验的资深 [领域] 专家，精通 [技术栈清单]，以及 [年份] 最新实践。
你具备 Goal-oriented 自主执行能力：必须先完成 Deep Research，再基于证据给出可落地的
生产级方案。

项目背景
[现状：已有什么、跑在什么上、规模如何]
[目标：要新增什么能力，核心新功能 1/2/3]

硬性约束（必须严格遵守）
1. [不可破坏的既有资产，例如「绝对不能影响现有 X 的代码/构建/发布/运行时行为」]
2. [组织方式约束，例如「新建独立文件夹，低耦合高内聚，靠接口契约连接」]
3. [其余领域约束]
4. 采用最新稳定架构与最佳实践，优先生产级、可维护、可扩展方案。
5. 本轮优先落地 [平台/范围]，但架构必须支持后续平滑扩展到 [其余平台/范围]。

本轮核心目标（Objective）
完成一次完整的 Deep Research + 架构设计，输出一份可直接指导开发团队落地的专业技术方案。

可验证完成标准（Done Criteria）
- 有完整、有证据支撑的技术选型对比与决策依据（必须引用最新资料与数据）
- 有明确推荐架构 + 详细的目录结构
- 有清晰的接口契约、数据流、权限模型
- 有分阶段实施 Roadmap（含可验证里程碑）
- 有风险分析与缓解措施
- 所有方案均明确说明如何满足上述硬性约束
- 整体方案达到生产级可落地标准，避免空泛建议

必须进行的 Deep Research 方向（必须先研究再结论，禁止拍脑袋）
1. [技术选型深度对比：候选 A / B / C，并列出必须覆盖的对比维度]
2. [组织方式：独立 folder vs workspace vs 共享包 + path 依赖 vs 接口契约]
3. [数据与权限模型：如何在不破坏既有 schema 的前提下实现 X]
4. [既有后端平台如何复用或扩展]
5. [初始化 / 依赖注入 / 绑定逻辑放哪里最安全]
6. [长期运行的后台服务如何设计]
7. [前端专属最佳实践：可视化 / 实时 / 多窗口 …]
8. [安全、性能、离线、发布与 CI/CD]
9. [与既有端共享类型/模型/客户端/业务逻辑的最佳方式]

输出格式要求（必须结构化、专业、可直接落地）
1. Deep Research 摘要：各选项最新状态、优劣势对比表、推荐结论 + 完整理由（可追溯到来源）
2. 架构决策记录（ADR）
3. 详细目录结构：完整树状，标注哪些共享、哪些专属、边界在哪
4. 接口契约与数据流（含权限与可见性的完整数据流）
5. 初始化 / Bootstrap 方案
6. 后台服务设计：角色、接口、与前端协作方式
7. 分阶段 Roadmap：Phase 0（骨架）→ 1（打通）→ 2（核心）→ 3（完善/安全/发布）
8. 风险清单与缓解措施
9. 关键代码骨架 / 伪代码（仅关键部分）

请严格按照「先 Deep Research → 再基于证据给出方案」的顺序执行。所有结论必须可追溯到
最新实践。开始执行。
```

### v2 补丁（追加在原版末尾）

```text
【执行纪律补充 · 必须遵守】

A. 仓内审计先于外部调研（顺序不可颠倒）
   动任何 WebSearch 之前，先把目标代码库摸一遍并输出一节「仓内实证审计」：真实的分层、
   真实的依赖、真实的授权模型、真实的 CI 触发范围、真实的测试规模。每条结论附一条
   可复现的命令。
   理由：外部调研只能告诉你「业界怎么做」，只有仓内审计能告诉你「这题在这个仓到底是
   什么形状」。

B. 你被授权推翻我的前提
   本 prompt 的技术前提是我的假设，不是事实。如果仓内审计显示某个前提不成立，请明确
   指出它不成立、给出证据、然后基于实况重新推导，不要为了迎合前提而硬套。
   在方案里单列一节「本 prompt 中不成立的前提」。

C. 数字纪律（最容易违反，且违反时最像没违反）
   · 每个数字必须来自可复现的命令、带 URL + 日期的一手来源，或明确标注「本机实测」。
   · 查不到就写「未找到一手资料」。禁止补位，禁止取整后当精确值。
   · 绝对禁止为一个数字编造一个听起来合理的解释——给数字配解释比不配更危险，
     它让读者以为你核过了。
   · 引用命令输出必须是真实输出。用过 head/tail/grep 截断的，必须先确认截断后的结论
     对全集仍然成立。
   · 公开资料可能被内容农场污染：凡引用 benchmark，必须能追到被测对象、机器、方法；
     追不到就剔除，并单列一节说明剔除了什么。

D. 自核验是交付的一部分，不是可选项
   交付前做一轮对抗式核验：把方案里所有「可验证」的断言拆出来逐条跑命令，默认自己
   写错了、目标是找错而不是确认对。判错的再做一轮独立复核（避免冤枉）。
   交付物里留一节「核验留痕」：核验多少条、确认多少条、改正多少条、哪几条是硬伤。

E. 区分「方案」与「决定」
   最后单列一节「需要你拍板的问题」，每条给出：我的默认假设、为什么这条是你的决策域
   而不是我的、最晚什么时候必须定。不要把产品决策伪装成技术结论。
```
