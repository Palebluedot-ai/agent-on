### pr-only-gate-lets-red-merge-and-taxes-successors(只在 PR 上跑的闸,红了也能合——代价由后来者付)
- source:Dartify @ e20fea3 | pin v0.9.1
- evidence:PR #117(D35 测量闭环)把 `app/pubspec.lock` 写进「必需存证输入」清单,而它被 `.gitignore` 的 `**/pubspec.lock` 挡着、永不进仓 ⇒ 干净 checkout 上 `hashFiles` 抛 `ENOENT: ... /app/pubspec.lock`。**#117 自己的 api job 就是红的**(job 93248349936)却被合进 main;此后我这条无关 PR 的 api job 报**同一条** ENOENT(job 93252992874)。main 上零症状——CI 里 api job 的触发条件是 `github.event_name == 'pull_request'`,main push 根本不跑。本地全绿(`npx tsc --noEmit` rc=0、`npx vitest run` 2434 passed)因为本机跑过 `flutter pub get` 有那个文件。先复现再修:把 `app/pubspec.lock` 挪走模拟干净 checkout → 修前 `2 failed`(同一条 ENOENT)、修后 `Test Files 2 passed / Tests 125 passed`。修复(挪进作者已有的 `existsSync` 过滤可选列)随 PR #119 squash 进 main @9899a66
- confidence:medium(单项目单次,但两条机理都普适:①PR-only 闸在 default branch 上没有回声 ②开发机文件系统恒富于干净 checkout)
- claim:**闸的触发面必须覆盖它要保护的分支**——只在 PR 上跑的检查,一旦红着合入就在 default branch 上永久静默,而**每一条后续 PR 都会替它买单**,且症状伪装成「我的改动弄坏了 CI」,归因成本极高。两条硬做法:①任何「本地绿 / CI 红」先查**被 .gitignore 的文件是否被当成必需输入**,别先怀疑环境;②凡把文件路径写进清单/存证/校验集,当场问一句「干净 checkout 上它在吗」——`git ls-tree <default> --name-only | grep -qxF <path>` 一行可验。合并红 PR 的人应当知道:红不会留在他自己身上
- suggested_landing:playbook CI/闸篇新增「闸的触发面 = 它要保护的分支」一节 + kit/merge-checklist 加一行「红着合 = 把红转嫁给后来者,禁止」;bench 案例
- rollback:revert 落地 commit
- trace:本会话;与 bench 既有「本地绿 CI 红」族同源但成因不同——那些是工具版本差异,这条是**仓的文件集差异**
- 状态:landed@同批（§三½.5 触发面 + merge 2c + bench 34）

### gate-reads-committed-history-not-worktree(闸读的是提交历史,不是工作区:不提交就跑等于空过)
- source:Dartify @ e20fea3 | pin v0.9.1
- evidence:`scripts/check_state.py` 有一条「两个真相面必须同一笔 commit 一起喂」的断言,实现是 `git log -1 --format=%H -- <path>` 比两个文件的最后提交。我改完 `docs/state/progress.yaml`(未提交)直接跑 `uv run --with pyyaml scripts/check_state.py` → **✅ 六项全部通过**;提交并推送后 CI 跑同一个脚本 → **❌「progress.yaml 最后更新于 6b8b134,而 dashboard.html 停在更早的 e78b7b5」**。同一份代码、同一个脚本,只差「有没有 commit」。这个假绿让我把一次本该本地发现的失败交给了 CI
- confidence:medium(单项目单次,但凡断言**跨文件/跨提交关系**的闸都有这个性质:同笔喂养、记账、blame 类、ancestor 类)
- claim:**断言涉及提交历史的闸,本地验证必须在 `git commit` 之后跑**;提交前跑出的绿只证明「工作区没坏」,不证明断言成立——它读不到你手里的改动。判别方法:闸里出现 `git log` / `git blame` / `git merge-base` / `git show <ref>:<path>` 任一,就归此类。写这类闸时应在脚本里显式提示(如工作区对目标文件有未提交改动时打 warning),别让「先跑后提交」的自然顺序制造假绿
- suggested_landing:playbook 机械闸篇加「闸的读取面:工作区 vs 提交历史」一节 + kit 的闸模板加一行 warning 惯例;bench 案例
- rollback:revert 落地 commit
- trace:本会话;修复记录在 Dartify commit(随 #119 squash @9899a66)的 message 里
- 状态:landed@同批（§三½.5 读取面 + merge 7h + bench 34）

### pushing-base-branch-dirties-own-open-pr(往 default branch 推一笔,会把自己在跑的 PR 撞成 DIRTY——且 CI 一个 job 都不触发)
- source:Dartify @ e20fea3 | pin v0.9.1
- evidence:为清记账欠账,按闸的指引推了一笔 `chore(state)` 直落 main(`db6e5a7`),它动的是 `docs/state/progress.yaml` + `dashboard.html` —— 恰好是我自己开着的 PR #119 也在改的两个文件。推完 `gh pr view 119 --json mergeable,mergeStateStatus` → **`CONFLICTING` / `DIRTY`**;`gh pr checks 119` 只剩 `GitGuardian Security Checks` 一行,**仓内 CI 一个 job 都没触发**(GitHub 不为 DIRTY 的 PR 起 checkout)。`gh run list --branch <分支>` 显示最新 run 仍钉在上一个 sha。rebase 解冲突后恢复九项全绿
- confidence:medium(单项目单次,但机理是 GitHub 行为,与仓无关)
- claim:**往 default branch 直推之前,先查有没有 PR 正在改同一批文件**(`gh pr list --state open` + 对比改动文件集)。撞上的症状极具误导性——PR 看着像「CI 坏了/CI 不跑了」,而真身是 PR 压根没进到能 checkout 的状态。凡「机制允许直落 default branch」的豁免(记账、hotfix、release chore),都要连带这条提醒:**豁免的是评审,不是并发影响**。判据一行:`gh pr view <n> --json mergeStateStatus` 出现 `DIRTY` 时,不要去查 CI 配置,去查 base 是不是刚动过
- suggested_landing:playbook 多会话并行篇 + kit/merge-checklist「直推 default branch 前置检查」;bench 案例
- rollback:revert 落地 commit
- trace:本会话;与 kit/worktree-gc-pattern 的「squash 换 hash 致新分支从旧 HEAD 长 → PR DIRTY + CI 不跑」是**同一副面孔的另一种成因**,消化时建议并卡:症状表相同(DIRTY + 零 job),病根一个是 base 前进、一个是分支起点错
- 状态:landed@同批（§三½.5 并发面 + merge 7d/7g + worktree-gc DIRTY 双成因 + bench 34）

### ledger-entries-dont-record-themselves(记账机制不记自己 ⇒ 欠账会自我繁殖)
- source:Dartify @ e20fea3 | pin v0.9.1
- evidence:`check_ledger` 报 11 条 merge 超 48h 宽限未入台账(#77~#89,72~118h),其中 **#81/#83/#86/#87/#88 五条本身就是 `chore(state)` 记账提交**——它们把别人记进来了,却没人回头记它们。另有隐私批十连 #106~#115 在 `progress.yaml` 与 `dashboard.html` **两个真相面一字未记**(不是漏号码,是整段工作没有记录)。一次补账 commit `db6e5a7` 清 24 条,清完 `python3 scripts/check_ledger.py` → `✅ SINCE 后所有 merged PR 均已入账`
- confidence:medium(单项目单次,但「元动作豁免自己」是所有记账/审计类机制的通病)
- claim:**记账类机制必须把「记账动作自身」纳入被记账集合**,否则元动作成为盲区、欠账自我繁殖。设计时问一句:「执行这条规则所产生的产物,受不受这条规则约束?」若答否,就是盲区。同族反模式:审计不审计审计者、备份不备份备份配置、监控不监控监控本身。补账时**补内容不补号码**——闸认的是「PR 号出现在台账原文」,只塞号码能骗过闸,但骗不过下一个来读台账的人
- suggested_landing:playbook 记账/棘轮相关篇 + kit 的 ledger 模板加「元动作自涵盖」检查行;bench 案例
- rollback:revert 落地 commit
- trace:本会话;与 v0.8.0 第二十次消化落地的 `ledger-ratchet-mechanism` 是同一机制的**下一层问题**(那张卡解决「无闸=自觉」,这张解决「闸有盲区」),消化时建议挂在同一节

### discriminating-probe-needs-unguessable-value(要证明约束真在生效,压力测试不够——需要一个只有约束成立才可能出现的值)
- source:Dartify @ e20fea3 | pin v0.9.1
- evidence:验「上游端点是否支持严格 `json_schema` 结构化输出」(该结论决定客户端降级是保险还是主力)。五发探针打真实端点:**A 对照**用现状的松 JSON,模型当场编了个白名单外的值;**B** 上 `json_schema`+`strict`,回了白名单内的值;**C 压力**明令输出枚举外的值,它仍回白名单内——看似证明 enum 生效,**但排除不掉「模型自己想通了」**;**D 判别**在 schema 里加一个提示词从未提及的暗号字段 `schema_marker: enum["ZQX-7788"]`,模型原样吐出 ⇒ 判定成立,schema 确实在驱动采样;**E** 递一个非法 schema(`type:'integer'` 配 `enum:['not-an-int']`)上游 **200 不报错**,顺着 enum 走 ⇒ 上游不校验 schema 合法性。结论落 `docs/research/2026-08-09-agent-nlp-navigation.md` §11.3.1 @e3ecebb(PR #143)
- confidence:high(方法论层,不依赖具体供应商;C 与 D 的区别可在任何「某约束是否生效」的场景复用)
- claim:**证明「某个约束真在生效」时,让被测方违反约束(压力测试)是弱证据——模型/系统可能出于别的原因恰好合规。强证据是构造一个「只有约束成立才可能出现」的可观测值**(提示词无法猜到的暗号、随机 nonce、超出训练分布的字面量),它出现即判定成立。配套第二问:**约束本身若写错,会不会有人告诉我?**——把一个明知非法的约束递进去,若系统照单全收(200 不报错),说明校验不存在,那么**下游的事后校验一条都不能撤**
- suggested_landing:playbook 反幻觉/取证篇新增「判别式探针 vs 压力测试」一节 + bench 案例;kit 的验证 checklist 加一行「你的证据能排除『它本来就会这么做』吗」
- rollback:revert 落地 commit
- trace:本会话;与既有 `anti-hallucination` 系列同族——那些管「别编」,这条管「怎么证明没编」
