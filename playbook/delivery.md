# 功能交付与检查节奏

> 职责边界：Agent-On 接入项目的日常交付约定；规定何时分工、验证、复查和交单。具体执行见 [交付入口](../kit/delivery-workflow.md)，合入权限仍由项目规则与值守政策决定。本文件不授予发布、派工或修改远端保护规则的权限。

来源：2026-10-25 用户反馈——窗口各做各的、CI/review 等待太久、需求持续变化；方法参考 Matt Pocock 1.3.1 的 codebase-design、implement、implement-spec、code-review、writing-for-agents。采用其工作包、局部反馈与两轴审查方法，不复制整套插件，也不要求安装 Matt 才能交付。

## 一个可交付批次

把当前目标推进到一段可使用、可验收、可单独合入的结果。有关联的小任务共用一次整体验收；有独立价值的成果及时交付，不等周末凑大 PR。

工作包只需能回答：要得到什么、谁负责、改哪里、依赖什么、怎样验收。复用项目已有任务、需求和决策来源；临时明确的小任务可以直接在当前上下文执行。跨窗口需要持续跟进时，再用现有 task/dispatch 回执，不新建另一套台账。

共享接口、路由、全局样式与锁文件先归一个负责人；消费者等前置成果实际合入。任务关系图只保留依赖和来源，代码关系图只看本次涉及区域。方向清楚就实现；长期方向未知才用决策地图。

## 检查时点

| 时点 | 默认行为 | 收尾条件 |
|---|---|---|
| 开发中 | 局部测试、失败复现、必要预览；代理自行推进 | 已得到本次修改的有效反馈，继续开发，不自动开启全仓 review |
| 一批成果可交付 | 一次当前需求与关键约定审查，验证受影响行为 | 没有影响本批验收的未解决缺陷；有价值的建议另行安排 |
| 合入前 | 当前候选的必需 CI、共享契约及相关安全/数据验证；值守取证、合入、记账 | 相关证据与项目实际合入条件满足，不等待周检 |
| 夜间定时 | 全仓回归、跨平台覆盖、较慢机械检查 | 复用现有 CI runner；失败保留证据并交负责人，正常保持安静 |
| 每周一次 | 架构、性能趋势与规则漂移 | 针对真实变化和反复问题复盘，不重跑同一套机械检查 |

生产发布、数据迁移、权限改变与高风险共享改动，提前执行相关完整验证。若合入 main 即生产部署，发布必需检查属于合入前。需求探索、纯文案和低风险文档用实际相关的检查，不为流程增加镜像测试。

影响范围包括消费者、依赖与检查器本身；无法可靠限定范围时扩大相关回归。夜间与周检补广度，不把当前相关失败、取消或未取得的必需证据当通过。仓库现有 required checks 在实际配置更改前继续生效。PR 工作流保留稳定的检查名称，在步骤内跳过无关运行；不能用整个 required workflow 的路径过滤制造永久 Pending。

周期任务复用项目现有 CI/宿主调度，一个项目只保留一份。安装模板或读到本文件不等于定时检查已经启用；只有已授权并取得真实运行回执才能报启用。具体技术栈命令从项目读取，不凭通用模板猜测。

## 审查与复查的边界

两轴分别回答：**当前需求实现了吗？关键项目约定满足了吗？** 工具已经执行的格式、类型等检查直接引用可信结果。Matt、GStack 与 kit 在同一阶段选择一套；低风险小改动可以由主会话核验，不默认再开审查窗口。

阻塞问题要有受影响行为、位置、证据和修正方向。涉及当前验收、安全、数据损失、真实回归或必需约定才阻塞；风格、可能更好的结构与范围外建议不能仅凭审查偏好升级为 changes-requested。删掉测试需判断它保护的行为是否仍被覆盖，不把等效测试重构一概判作严重缺陷。

修复后复查修复点及其影响范围。已有可信证据锚定提交、测试输入和环境，三者相关部分未变就复用；代码、依赖或集成环境改变影响结论才补跑。真正的新问题继续处理，已通过部分不因窗口多或结束一轮而从头重审。

高风险独立审计仍由不同执行者取证；需要推翻具体可疑证据时独立复现，不要求每名审查者把所有命令重跑一遍。正常审查可以没有发现。

## 需求变化与少打断

用户明确改变要求后，就地更新工作包的当前验收和来源，标明旧假设作废，沿新范围继续。若影响其他窗口，只通过当前授权路由通知相关负责人；其余工作继续。用户提出想法但未要求实施时进入已有待办，不扩当前范围。

代码、记录与现有授权能回答的问题由代理自己查。可逆实施选择自行决定；仅在产品方向确实不明、缺少必要输入或越出已有授权时提问。等待检查由代理跟进；只在卡点、完成或需要用户决策时报告，不把每次轮询变成通知。

## 交付与改进

分别报告已实现、已验证、已合入、已发布/安装；结果回执和宿主退出不自动升级这些状态。功能窗口交单后由值守按既有规则合入；下一工作包消费真实合入证据。

返工、误拦、重复传话或无效规则出现时，先修当前原因，复用已有记录保存必要证据。共享问题才回流 intake；settle/digest 用于批量补收与维护者整理，不要求每个成功任务再做一次结账。

衡量收益看交付等待、用户转述/打断、重复检查与合入后回退。没有基线就记录事实，不新增每任务必填评分表，也不以审查轮数和规则数量表示质量。
